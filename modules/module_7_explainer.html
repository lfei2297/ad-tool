🎯 两种运行模式对比

模式一

广度优先，不补齐

  • 账号内同一 SKU 绝对不重复
  • 主品类用尽即停止，不跨品类补齐
  • 宁缺毋滥，严格去重
  • 适用于品类资源充足场景
模式二

不足补齐（推荐）

  • 允许同 SKU 不同素材（禁止同组合）
  • 主品类耗尽后自动切后备品类补齐
  • 后备按环形指针均摊，防止账号扎堆拿同样素材
  • 适合品类资源不均衡、需跨品类填充场景
核心区别：模式一 strict_unique_sku=True（SKU 在账号内只出现一次），模式二 strict_unique_sku=False（允许同 SKU 不同素材变体）。

def make_combo_key(item): sku = _sku_id(item) # 虚拟SKU优先，否则真实SKU lp = str(item.get("着陆页版本名称", "")).strip() mat = str(item.get("广告素材版本名称", "")).strip() return (sku, lp, mat) # 三元组作为唯一标识

🔬 算法逐阶段详解

🌿 阶段 1 — 各SKU第1变体（广度优先）

按 SKU 出现顺序遍历，每个 SKU 只取第 1 个变体，全局未使用的组合才能被选中。

def _sku_blocked(sku):
    return strict_unique_sku and sku in acc_used_skus  # 模式一下整SKU跳过

for sku in ordered_skus:                              # 按首次出现顺序
    if len(selected_items) >= target_count: break
    if sku in acc_used_skus: continue                 # 账号内已用过该SKU
    item = sku_group[sku][0]                           # 取第1变体
    combo_k = make_combo_key(item)
    if combo_k in globally_consumed_combos: continue   # 全局已耗尽则跳过
    _pick_item(...)
效果：确保每个账号优先拿到不同 SKU 的首条变体，最大化 SKU 覆盖广度。

🔁 阶段 2 — 全局未用变体（深度补齐）

阶段1填不满时，按变体索引 d 从 1、2、3… 逐层往下找，直到填满目标数量或所有变体耗尽。

for d in range(max_depth):                         # d = 变体深度索引
    for sku in ordered_skus:
        if len(selected_items) >= target_count: break
        if _sku_blocked(sku): continue
        if d >= len(items): continue                  # 该SKU没有第d个变体
        item = items[d]                               # 取第d个变体
        combo_k = make_combo_key(item)
        if combo_k in globally_consumed_combos: continue
        _pick_item(...)
效果：当某个 SKU 有多个变体时（如同一 SKU 的不同着陆页），优先把每个 SKU 的所有变体都用上，而不是一个 SKU 拿到底。

🔄 阶段 3 — 跨账号顺延复用（环形指针）

前两阶段全库耗尽后，按环形指针从上次停下的位置继续取，禁止每个账号都从池子开头重拿相同组合。

# 展开全部素材成一维数组（保持SKU顺序）
flat = _flatten_pool_items(sku_group, ordered_skus)
n = len(flat)
start = phase3_pointer % n                            # 从上次偏移接续

for step in range(n):
    idx = (start + step) % n                          # 环形遍历
    item = flat[idx]
    if _sku_blocked(sku): continue
    if combo_k in acc_used_combos: continue           # 账号内防重
    _pick_item(...)
    last_pick_next = (idx + 1) % n                   # 记录下次起点
phase3_pointer = last_pick_next                       # 更新指针供下个账号接续
关键设计：phase3_pointer 存在 phase3_pointers[category] 中，每个主品类独立维护。账号3不会重复账号1/2从池头拿的组合。

🆘 阶段 4 — 后备品类环形补齐（模式二专属）

后备品类也有自己的环形指针 global_fallback_pointer，三 Pass 策略：

# Pass1: 优先全局未用的"独立SKU第1变体"（DEF类优于ABC类素材2）
_round_robin("first_free")

# Pass2: 再取全局未用的其他变体（含同SKU素材2）
_round_robin("any_free")

# Pass3: 全局干涸 → 账号内未出现过的组合复用凑满
_round_robin("reuse")
为什么分三 Pass：后备品类往往来自不同类目，优先保证"独立感"（每个SKU各一个变体），再允许同SKU多素材，最后才复用。模拟人工分配逻辑。

🔐 防重机制的三层防护

globally_consumed_combos
全局层：跨账号共享，一个组合只要任一账号用过就标记消耗
acc_used_skus
SKU去重层（模式一）：同一账号内同一 SKU 只允许出现一次
acc_used_combos
账号内层：同一账号内同一组合（SKU+着陆页+素材）只出现一次

🧠 为什么这样设计？设计意图拆解

问题

账号间组合重复

  • 如果每个账号都从池头重拿，账号3/4拿到和1/2完全相同的组合
  • 广告测试失去意义——不同账号跑的是相同素材
解法

环形指针接续

  • phase3_pointer 跨账号接续，后账号从上次停下的位置继续
  • 每个主品类有独立指针，后备品类另有独立指针
问题

账号内SKU重复

  • 一个账号拿了 SKU-A 的变体1，下次又拿变体2，账号内扎堆
  • 覆盖度低，无法测试更多 SKU
解法

阶段1广度优先

  • 先遍历所有 SKU 的第1变体，确保账号内每个 SKU 最多出现一次
  • 模式二放宽：允许同 SKU 不同素材，提高填充率

🔢 关键数值约束

phase3_pointer
跨账号接续，品类维度独立。账号1用掉3个后指针=3，账号2从位置3继续拿
global_fallback_pointer
后备品类独立环形指针，与主品类指针互不影响
max_depth
最深 SKU 的变体数量 = 阶段2外层循环上界
total_slots
后备品类总素材数 = reuse 模式的无进展停止上限（防止死循环）

⚠️ 潜在风险点

品类名严格匹配
账号表填的品类名必须与SKU表"商品分类"列完全一致（包括空格），否则匹配不到资源池
NaN 处理
_sku_id 用 .lower() != "nan" 判断，Excel 导出时某些库可能输出 NaN 而非字符串，需注意
模式二循环风险
total_slots 作为无进展上限，但模式二 reuse 阶段理论上可能真的填不满（资源彻底枯竭），此时函数正常返回缺口
session_state 清空时机
只有上传新文件才清空旧数据，重复点击按钮不会触发重新计算（需重新上传文件或加重新计算按钮）
